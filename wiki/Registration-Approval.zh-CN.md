# 新用户注册审核

简体中文 | [English](Registration-Approval.md) | [Wiki 首页](Home.md)

注册支持三种模式，由服务器管理员设置。已有正常账号默认继续使用，不需要重新审核；升级不会改变原来的注册方式。

| `registrationMode` | 注册行为 |
| --- | --- |
| `open`（省略时的默认值） | 注册成功即可登录 |
| `approval` | 提交注册申请，由管理员或授权审核者通过后才能登录 |
| `closed` | 关闭新用户注册，已有账号仍可登录；找回密码依赖原有邮件配置 |

## 开启审核

先完成新版后端、前端和数据库升级，见 [一键升级](Upgrade.zh-CN.md)。编辑实例的 `config/backend.yaml`，在**已有**的 `preference.security` 下加入一行，不要重复创建顶层 `preference`：

```yaml
preference:
  security:
    registrationMode: approval
    # 保留这里原有的 requireEmailVerification 等所有设置
```

默认路径是 `/opt/LibreOJ/config/backend.yaml`。以上仅展示需要修改的局部，不能用它覆盖完整文件。模式只接受小写 `open`、`approval`、`closed`；错误值会阻止后端启动。

配置在后端启动时读取。保存后重启后端；完整部署还需确认本机评测服务已重新运行，因为其服务依赖后端。默认服务名的操作示例：

```bash
sudo systemctl restart libreoj-backend.service
# 仅 all 部署 / 已启用本机评测时执行：
sudo systemctl start libreoj-judge.service
```

刷新浏览器后，新模式生效。如果以前在 Nginx 增加过拦截 `/api/auth/register` 的规则，需要在启用审核注册时手动移除该拦截并检查、重载 Nginx，否则注册请求仍会被入口阻止。升级器会保留已有 Nginx 配置。

## 用户与审核者流程

1. 用户填写用户名、邮箱和密码。若站点要求邮箱验证码，仍需先完成邮箱验证；邮箱验证与人工审核是两个独立步骤。
2. 提交后页面显示等待审核。系统只保存独立申请及密码哈希，不创建主站账户、不占用主站用户 ID、不返回登录令牌。申请不会出现在用户列表或个人主页中。
3. 站点管理员或授权审核者登录，通过用户菜单中的“注册审核”打开 `/registration-reviews`。
4. 按待审核、已通过、已拒绝或全部筛选申请。状态以对应颜色的文字显示；可查看用户名、邮箱、申请时间和审核记录，分页处理。待审核和已拒绝项不显示主站用户 ID。
5. 待审核申请可选择通过或拒绝；已拒绝申请可再次选择通过。可填写最多 500 字的审核备注。通过时，系统在一个事务中创建账户、分配主站用户 ID 并保存审核记录，用户可使用申请时的密码登录。拒绝只记录审核结果，不会创建账户或个人主页。

站点管理员（`isAdmin`）始终可以审核；普通用户默认无权。管理员可在“权限管理”页面（`/permissions`）选择审核者账号，在管理特权中将 `ManageRegistrationReviews` 设为“允许”并保存。审核者刷新页面后可查看申请邮箱、内部备注及审核队列，并作出决定。撤销时将该项设为“拒绝”；仅有用户组管理或“管理用户”权限不会自动获得审核权。审核者还须具有 `ViewSite` 站点访问权限（普通用户默认已有）；被拒绝访问站点的账号不能仅凭审核权限执行审核。

该权限不授予“详细权限管理（仅管理员）”或管理员身份。授权审核者不能使用权限管理接口给自己或别人加权，也不能修改站点管理员资料或密码来取得管理员身份。权限存储在数据库，无需新增 YAML 设置或重启；菜单可能需要刷新，但后端会按当前权限核验请求。

审核结果、审核人、时间和备注保存在数据库，并写入审计日志。备注只对管理员及授权审核者显示；用户登录失败时看到等待审核或申请被拒绝的提示，不显示内部备注。目前不自动发送审核结果邮件。

## 状态与兼容性

- 老账号和 `open` 模式新建的账号没有审核记录，视为已激活；站点管理员账号不受审核门槛影响。
- `approval` 模式在独立申请表中保留用户名和邮箱。申请编号与主站用户 ID 是不同概念，前者仅供审核接口定位申请。待审核或被拒绝的申请没有正式用户身份，不能通过登录或重置密码取得会话。
- 从 `approval` 切回 `open`，只影响后续注册；已有待审核申请仍需处理。切到 `closed` 也不会删除申请，管理员及授权审核者仍可审核。
- 重复提交同一决定不会重复开户或写入审计日志。并发审核按数据库锁顺序处理；通过后不可再拒绝，先拒绝的申请仍可在后续审核中获批。
- 已拒绝申请可改为通过：成功时才创建账户、分配新的主站用户 ID，并记录从 `rejected` 到 `approved` 的审核日志，原拒绝记录保留。若用户名或邮箱已被占用，操作失败并保持原状态，不创建账户；先由管理员处理冲突，再重试审核。已通过申请不能改回拒绝。未通过期间用户名和邮箱继续保留，不提供重新申请或删除申请按钮，也不要直接删除数据库行绕过历史。
- 此功能控制账号激活，不会把原本公开的题目、讨论等游客可见内容改为私有，也不是全站访问白名单。

## 数据库与排错

新版使用独立的 `registration_application` 表，保留旧 `registration_review` 表以兼容已通过的历史记录。原 `user` 表不增加必填列；已有正常账户的 ID、密码和内容保持不变。委派审核沿用现有权限表；升级器仅在 `user_privilege.privilegeType` 的已知枚举末尾追加 `ManageRegistrationReviews`，保留原值和顺序，不新增配置或业务表。

从上一版注册审核升级时，请使用新版升级脚本，不能只替换网页或重启后端。脚本先备份并在数据库副本中验证，将旧待审核／已拒绝的空账户转为独立申请，保存密码哈希、申请时间与审核信息，再移除对应未激活账户的空记录。旧待审核申请获批时再创建新账户。已经消耗的历史 ID 不会回收，后续用户 ID 允许存在间隙。旧空账户自己的正常注册／密码输错日志完整转存为申请的内部审计档案，不会公开返回；管理员审核日志仍保留并关联申请。

迁移只处理符合旧版自动注册默认值、没有业务内容或自定义权限的未激活账户。若存在提交、题目、讨论、权限、定制资料、未知关联、跨库外键或申请身份冲突，升级会停止并保留原数据，需先人工审查，不能强制删除来绕过。已通过审核的历史账户继续使用原 ID。

迁移后若切换失败，不能直接恢复忽略独立申请的旧代码；升级器可能为保护注册审核状态而保持应用停止。应保留新版数据并修复部署，详见 [升级与恢复](Upgrade.zh-CN.md)。

如果页面没有审核入口，先确认账号是站点管理员或已获授 `ManageRegistrationReviews`，然后刷新前端。若仍然出现旧页面，确认本次前后端均已更新。如果后端报告审核表不存在，应按升级日志检查数据库迁移；不要通过关闭 AppArmor、放宽目录权限或删除旧数据库解决。

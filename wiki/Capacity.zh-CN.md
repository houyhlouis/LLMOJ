# 容量

简体中文 | [English](Capacity.md) | [Wiki 首页](Home.md) | [安装后运维](Operations-Configuration.zh-CN.md)

本页记录一个小型网站在实测负载下的表现，供估算服务器规模参考。你的结果取决于硬件、数据和访问者；要观察自己的网站，见[指标](Operations-Configuration.zh-CN.md#指标)。

## 测量内容

| | |
| --- | --- |
| 服务器 | Intel Core i7-11370H（4 核 8 线程），3.3 GiB 内存，SSD，Ubuntu 26.04。MariaDB 11.8、Redis 和 MinIO 在同一台服务器上；一个后端进程（`server.clusters: null`，与安装时相同）；一台评测机，2 个评测槽位，使用一个 CPU。 |
| 数据（合成） | 2,000 个用户；1,500 道题目（1,400 道公开），每道有两种语言的题面和两个标签；一年内的 300,000 个练习提交；30 场比赛，每场 6 道题（已结束的约 1,000 个提交，进行中的一场 2,551 个）；3,000 个讨论，每个 5 条回复；300 个 50 道题的题单和一个 1,000 道题的题单。数据共约 300 MB。 |
| 访问者 | 页面访问以固定速率到来。每次访问发送该页面在浏览器中发送的 API 请求（用 Chromium 录制），题目、提交、用户和讨论各不相同。75% 已登录。比例：进行中的比赛 20%，其排名 10%，题目 20%，提交列表 12%，单个提交 8%，题库 8%，首页 6%，其余为其他比赛、讨论、用户和题单。 |
| 评测 | 全程每 2 秒一个 C++ 提交，真实评测 |
| 速率 | 每秒 20 次页面访问，持续 2 分钟，约相当于 300 名学生参加比赛、每人每 15 秒刷新一次；然后每秒 40 次持续 90 秒，每秒 80 次持续 60 秒 |
| 版本 | 测量的版本是 `5a1d5cf`（2026-10-18）；下文的“本版本之前”是它的上一个提交 `3f1c52d`。 |
| 负载 | 这次测量所用的脚本没有保留下来。现在的[性能测试工具](https://github.com/houyhlouis/LLMOJ/tree/main/deploy/benchmark)可以重新生成相同的数据和页面比例，见[重复这项测量](#重复这项测量)。 |

请求直接发送到后端，不经过 Nginx 和 TLS。所有模拟访问者共用一个地址，因此关闭了限流。

## 结果

| 每秒页面访问 | 每秒请求 | 页面访问 p50 / p95 | 请求 p95 | 等待评测 p95 | 后端 CPU 平均 / 峰值 | MariaDB CPU |
| --- | --- | --- | --- | --- | --- | --- |
| 20 | 29 | 12 / 35 毫秒 | 20 毫秒 | 16 毫秒 | 28% / 63% | 11% |
| 40 | 59 | 11 / 30 毫秒 | 16 毫秒 | 14 毫秒 | 40% / 57% | 19% |
| 80 | 116 | 12 / 37 毫秒 | 22 毫秒 | 19 毫秒 | 71% / 95% | 34% |

没有请求失败。后端约使用 450 MB 内存，MariaDB 约 200 MB。100% CPU 即一个核。

最慢的页面是 1,000 道题的题单（约 100 毫秒）。所提出的“页面读取 p95 低于 300 毫秒”的目标在三种速率下都远远达到。在每秒约 120 个请求时，后端进程用掉一个核的大部分，这台服务器的单个进程会在这附近达到上限。运行多个后端进程（`server.clusters`）不在本次测量范围内。

### 本版本之前

同样的负载作用于上一版本：每秒 20 次页面访问时，页面中位数耗时 6.2 秒、p95 15.5 秒，提交最多等待评测 90 秒。后端进程已饱和（计入垃圾回收为 152% CPU），每秒 40 次时落后数分钟。比赛页面每次访问都从比赛的全部提交计算排名，题库对每道题分别读取标签，题单对每道题分别读取（1,000 道题 2,118 次查询）。现在：

| 页面 | 查询次数 之前 → 现在 | 耗时 之前 → 现在（逐个请求） |
| --- | --- | --- |
| 进行中的比赛、排名 | 13–14 → 12–13，排名在提交变化之前一直复用 | 75–115 毫秒 → 9–20 毫秒 |
| 题库（50 道题） | 103–109 → 5–11 | 31–49 毫秒 → 11–19 毫秒 |
| 1,000 道题的题单 | 2,118 → 120 | 1,242 毫秒 → 108 毫秒 |
| 讨论 | 24–50 → 13–18 | 10–19 毫秒 → 7–12 毫秒 |

打开的比赛页面在打开时只请求一次比赛详情（之前是两次），并在浏览器标签页隐藏期间停止刷新。

## 缓存的结果

一些结果会在请求之间保留：

| 内容 | 最长保留 | 何时重新计算 |
| --- | --- | --- |
| 题目发给评测机的评测设置（包括从数据中找到的测试点），存于 Redis | 5 分钟 | 设置、测试数据或类型改变时 |
| 题目的练习统计（分数分布，以及最快、最省内存、最早的通过提交），存于 Redis | 60 秒 | 提交的结果改变时：评测、重测、Fake、Hacked 或删除 |
| 比赛的成绩，存于每个后端进程 | 60 秒 | 比赛的任一提交改变时 |

每次改变都会推进缓存结果的代数，因此在改变之前开始读取旧数据的请求，之后无法再把旧结果存进缓存。如果改变时无法连接 Redis，做出改变的后端会在 Redis 恢复后立即丢弃该缓存结果，其他情况下最多显示上表所列的时间。没有 Redis 时，每次都从数据库计算。自 2026 年 11 月起，这些 Redis 条目使用新名称：升级时不需要清空 Redis，旧条目不再被读取（30 天内自行过期）。

## 数据库索引

用 MariaDB 慢查询日志（阈值 0 秒）记录了这些页面的全部后端查询，并检查了它们的执行计划。没有慢查询：单个查询检查的行数最多为 4,500（统计可见的讨论）。在 330,000 个提交上，提交列表按各个筛选条件（题目、用户、状态、语言及其组合）查询都在 3 到 19 毫秒内完成，使用的是已有的组合索引。因此本版本没有增加索引。

## 严格 IOI 计分

计算严格 IOI 比赛的成绩时，需要读取每个提交的评测结果中的子任务。2026 年 11 月之前的版本会读取每个提交保存的全部详情，包括源代码；现在只读取评测结果。2026-11-20 在上述服务器上用 `deploy/benchmark/strict-ioi.mjs` 测量（MariaDB 11.8，一场已结束的严格 IOI 比赛，1,000 个提交，每个源代码 64 KiB；两种方式使用同一构建）：

| 读取方式 | 从 MariaDB 读取 | 用时 | 计分进程的内存峰值 |
| --- | --- | --- | --- |
| 整行详情（以前） | 66.2 MB | 204 ms | 372 MiB |
| 仅评测结果（现在） | 0.58 MB | 35 ms | 143 MiB |

两者得到相同的成绩：工具会比较全部排名行的摘要。内存峰值包含后端自身启动所用的约 140 MiB。

## 重复这项测量

`deploy/benchmark` 中的工具在一次性的环境上进行这类测量（见[本地开发](Development.zh-CN.md)），绝不在真实站点上进行：

| 文件 | 作用 |
| --- | --- |
| `seed.mjs` | 把上述合成数据写入一个新数据库：相同的 `--seed` 和 `--as-of` 日期得到相同的数据，大小任意（`--scale 0.1` 为十分之一）。`--strict-submissions N` 和 `--source-bytes N` 会添加一场已结束的严格 IOI 比赛，供 `strict-ioi.mjs` 使用。它拒绝已有数据的数据库；名称不以 `llmoj_bench` 或 `llmoj_dev` 开头的数据库，除非给出 `--yes-this-is-disposable`，也会拒绝。 |
| `capacity.json` | 页面比例：每个页面发送的 API 请求（与站点页面的发送方式相同）及其在页面访问中所占的比例。 |
| `load.mjs` | 以固定速率打开页面，不论回答快慢（`--rate`、`--seconds`、`--signed-in`），报告每个页面和每种 API 请求的 p50、p95 和最大值、错误以及实际达到的速率，写入 `PREFIX.json` 和 `PREFIX.txt`（`--out PREFIX`）。加上 `--metrics-url` 时，还会报告每个请求的 SQL 查询数、后端的内存和评测队列的等待时间。发送任何请求之前，它会确认对方是生成了数据的那套环境；对不在本机上的地址，需要 `--yes-this-is-disposable`。 |
| `metrics.mjs` | 比较后端指标的两次读数，供 `load.mjs` 使用。 |
| `strict-ioi.mjs` | 上面的严格 IOI 对比。 |

第一张表中的各个速率，完整规模：

```bash
BENCH=/var/tmp/llmoj-capacity-$(id -u)
node deploy/dev/stack.mjs start --dir "$BENCH" --base-port 28600
# 所有模拟访问者的地址相同：现在把 "$BENCH/backend.yaml" 中的 security.rateLimit 设为 null
node deploy/benchmark/seed.mjs --config "$BENCH/backend.yaml" --seed 42 --as-of 2025-01-01 --scale 1
```

然后在另一个终端中启动这套环境的后端：`(cd apps/backend && . "$BENCH/backend.env" && node dist/main)`，再运行：

```bash
for run in '20 120' '40 90' '80 60'; do
  read -r rate seconds <<< "$run"
  node deploy/benchmark/load.mjs --manifest "$BENCH/benchmark.json" --seed 42 --signed-in 0.75 \
    --metrics-url http://127.0.0.1:28601/metrics --rate "$rate" --seconds "$seconds" --out "load-$rate"
done
```

结束后停止后端，并用 `node deploy/dev/stack.mjs reset --dir "$BENCH"` 删除这套环境。

这套工具不重现以下内容：

- **评测。** 上面的测量全程每 2 秒评测一个 C++ 提交。工具中的题目关闭了评测，提交也都已有结果，所以只测量页面读取；要测量等待评测的时间，请另外连接评测机并提交。
- **较小页面的比例。** 最后 16% 的页面访问如何分配给其他比赛、讨论、用户和题单，当时没有记录：工具给每类 4%。每个比例都可以在 `capacity.json` 中修改。
- **浏览器。** 请求直接发送到后端：不包括静态文件、Nginx 和 TLS，也不包括实时更新、轮询和访问者打开的筛选。
- **CPU 与缓存。** 工具不记录 CPU 使用率（运行时用 `top` 或 `pidstat` 观察），后端也不导出缓存命中或未命中的计数。
- **同一台机器。** 除非在别处运行 `load.mjs`，它与被测服务共用一台机器。

发布结果时，请保留 JSON 文件，并记下版本（`git rev-parse HEAD`，以及显示未提交修改的 `git status --short`）、机器（CPU、内存、操作系统、MariaDB 和 Redis 版本）以及缓存是否已预热。只比较在同一台机器上用相同方式得到的两个版本的结果。

2026-11-20 在上述服务器上，用当天的代码以十分之一的规模（`--scale 0.1`，种子 42）、关闭限流且没有评测检查了这套工具：每秒 20 次页面访问持续 60 秒，p50 为 9.4 ms、p95 为 17.5 ms；每秒 40 次持续 30 秒，分别为 7.8 ms 和 13.7 ms；没有错误，每个请求约 11 次 SQL 查询。这说明工具可以正常工作；这些数字不能与上面的完整规模结果比较。

# AI integration

`AiModule` provides authenticated, owner-scoped LLM and search/MCP configuration and durable jobs under `/api/ai/`. Supported actions include statement import and translation, source discovery, tags, difficulty, tutorials and sandboxed test-data generation. Generated problems remain private, and every write rechecks the current user's permissions and problem snapshot.

## Prompt and content languages

Repository-maintained system instructions, task prompts and injected formatting/protocol/scoring rules use English. This includes image extraction and OCR verification, statement translation, source discovery and verification, tutorials, tags, difficulty calibration, test-data plans, generators, validators, checkers, protocol judges, reference/independent solutions, quality probes and generator repair. The prompt regression suite follows model call sites and imported instruction fragments to check this convention.

Instruction language does not change content language. Extraction preserves the original statement language; translation follows its requested locale; `zh_CN` output remains Chinese and `en_US` output remains English. Bilingual tutorial/tag/explanation requirements and JSON keys remain intact. Original statements, quotations, search results, code and user input stay untrusted data in their original language. Chinese parsing expressions and localized editor/UI labels remain in place.

## Credentials and configuration

Provider credentials are encrypted with AES-256-GCM. Configuration responses expose `hasKey` without returning saved API keys. Saving a new provider URL clears the old key unless a replacement is supplied. The frontend clears submitted keys; request bodies, provider error bodies and keys are excluded from AI diagnostics and usage records.

`HYHOJ_AI_STATE_DIR` selects the private key directory. The backend creates a 32-byte `master.key` with mode `0600` inside a directory with mode `0700` and verifies ownership and file type. Keep this file outside the source repository. An existing encrypted database requires its matching original key; a missing key causes startup to fail. Private database backups must include the corresponding key and must never be committed or distributed with source code.

Provider requests support HTTP/HTTPS. Public destinations are open to every user; private, loopback and link-local destinations require a site administrator's own configuration (the runtime's `allowPrivateNetwork`) or a host listed in `HYHOJ_AI_PRIVATE_HOSTS`. Every resolved address is checked, and DNS lookup results remain pinned to each connection. Model listing and connection tests are bounded per user and site-wide. Redirects and credential-bearing Base URLs remain rejected; account permissions and owner-scoped key storage are unchanged. Model output limits and API capabilities remain provider-specific; the application validates its configured limits before issuing a request.

`HYHOJ_AI_SAMPLE_INPUTS_DIR` and `HYHOJ_AI_GENERATED_DIR` select private temporary work directories. Backend and judge configuration must agree on the sandbox input paths and runner socket. Generated programs execute in the judge sandbox. Its root filesystem and compiler dependencies are supplied separately from the source repository.

AI jobs use bounded concurrency, resumable checkpoints and cancellation checks. Source discovery requires search evidence and semantic verification. Test-data installation validates generated input, applicable samples, the traditional-task quality gate and permissions before activating the new judge configuration. Usage records contain request metadata and reported usage counts, without credentials or prompt/response bodies.

## Test-data quality gate

Traditional problems use three independent checks before new data is activated:

1. A separately generated small-input generator and brute-force oracle check the reference solution on at least 64 legal boundary and random inputs, with at least one input for every subtask. The input validator also checks these inputs. The oracle is requested separately from the reference solution; it uses a simpler exhaustive method rather than copying the optimized implementation.
2. A separately generated alternative correct algorithm must pass every final input using the configured checker and the problem's time and memory limits. Multiple valid witnesses and floating-point answers are compared using the actual checker, rather than byte equality.
3. Concrete wrong or excessively slow candidate programs are executed against the final dataset. Every candidate must fail on a legal case from its applicable subtasks. The runner can search a bounded number of additional targeted inputs and replace cases while retaining subtask scores. Each replacement is checked by the input validator, reference solution and alternative correct solution before it enters the dataset.

The plan records permitted correct algorithms and identifies each wrong or slow candidate's assumption, applicable subtasks and a concrete adversarial construction. SPFA is a slow target only when the legal graph family and resource limits make it inappropriate; the plan must retain other efficient correct methods. Every slow candidate must pass all applicable small differential inputs. A slow target requires TLE or MLE on a full-size legal input; WA or RE is a faulty implementation, not evidence of algorithmic degeneration. A candidate compilation failure, checker failure or sandbox infrastructure failure does not count as a successful rejection. All candidates must be rejected, all differential inputs must pass and all alternative-solution checks must pass; incomplete or inconsistent reports stop publication.

The oracle, small-input generator, alternative solution and challenge programs are private validation helpers and are not published as problem files. Existing generated make.cpp, std.cpp and validator.cpp artifacts are retained, and data.yaml includes the quality report.

The final report records differential counts and each rejected candidate's final case index and verdict (WA, RE, TLE or MLE). This provides evidence against the chosen candidate programs, not a proof that every possible incorrect implementation is rejected. Cases use fresh randomness, so reported final inputs are the reproducible counterexamples; a case index is not a random seed. The number of inputs, models and adversarial attempts is bounded to protect the shared judging queue.

Selection is coverage-aware (review Part III, W05):

- **Capacity.** `allocateAiTestcases` (`ai-case-allocation.ts`) shares cases out by subtask points, then, once the quality plan is known and before any program is written, gives every target a constructible slot. A target has one when one of its subtasks has at least 3 cases (indices 1 and 2 are the minimum and maximum). For each target without one, its applicable subtask with the most cases is raised to 2 plus the number of slot-less targets assigned to it. Cases carry no points of their own, so subtask points are unchanged and only the per-case share differs. The changes are recorded as `allocation.capacity` (`{ subtask, from, to, targets }`, warning `CASE_CAPACITY_ADJUSTED`); `pointsPerCase` is kept only when every subtask's share is the same. The total stays within 1,000.
- **Search and replacement** (`apps/judge/src/aiQuality.ts`). Extra search runs for a surviving target whenever one of its subtasks has a non-boundary case, witness or not. Each candidate (a search input, or a promoted small counterexample) is validated, answered by the reference solution, cross-checked by the alternatives and run against every applicable challenge, including rejected ones: its complete row. It replaces, in its subtask, a non-boundary case that witnesses nothing, or else a witness case whose witnessed targets the candidate rejects too (the witnesses move to it); otherwise it's unplaced. `stoppedBy: "capacity"` now means no non-boundary case at all.
- **Promotion.** A wrong challenge's first small differential failure is kept whole (up to 1 MiB). It is legal for its subtask, and the reference solution and every alternative agreed with the oracle on it. If the challenge survives the final cases, it's tried as a candidate before any generated search input.
- **Receipt.** `validation.quality` (version 1) adds optional fields; receipts of older judges have none of them, and the job shows nothing new for them:
  - `fuzzDistinct`: distinct differential inputs, by SHA-256;
  - `challengeResults[].tested` and `.kills`: final cases each challenge was run on, and how many rejected it;
  - `replacements`: `{ case, source: "search" | "small_counterexample", kills, moved }`;
  - `search`: `{ attempts, budget, found, unplaced, promoted }`;
  - `matrix`: per final case with any challenge run, the ids it `killed` and those that `passed`. A challenge isn't run on cases after its first rejection, so those cells stay unknown.

  The backend checks these fields against the request and the cases, counts distinct final inputs from the corpus (`corpus.distinct`), and warns about repeats (`DIFFERENTIAL_INPUTS_REPEATED`, `FINAL_CASES_REPEATED`); repeats are reported, not refused. `data.yaml` records all of it under `generation`.

Interactive and communication problems keep their existing hidden-state and protocol validation. Their jobs explicitly report that the independent brute-force and wrong-algorithm quality gate currently applies only to traditional problems.

## Judging contract

A test-data job works within its problem's judging contract (review Part III, W02), resolved by `ai-judging-contract.ts` before the job spends anything on programs.

- **Execution profiles.** Each role of a run (`std`, `alternative`, `challenge`, `oracle`, `generator`, `validator`, `checker`, `interactor`, `manager`) has a profile: C++ compile options, time and memory limits, CPU class (user program, checker or interactor, as the judge runs it) and whether it's compiled with the bundled `testlib.h` and the problem's extra source files. The shared type and parser are `packages/judge-protocol/src/ai-profile.ts`. A checker, interactor or manager the problem already has keeps its own options and limits (the problem's where it has none); one the job writes gets the defaults and explicit limits of at least 5,000 ms and 256 MiB (at least the problem's), which it is published with. Solutions run with the problem's limits and file I/O, the job's own programs (generators, validator, oracle) with 5,000 ms and 512 MiB, and Self Eval runs the published generator and validator with those too (`selfEval.limits`). Helper settings the job can't check with (other options, limits above 60 s or 4,096 MiB) are refused before the plan (`AI_HELPER_SETTINGS_UNSUPPORTED`).
- **The runner.** The AI runner (judge protocol 7 and later) compiles and runs every program with its role's profile and nothing else, and reports the profiles' digest with its result; a result without it is refused (`INVALID_SANDBOX_RESPONSE`). Only judges of the current AI execution protocol (8, see below) are sent AI runs. A request without profiles, from an older backend, runs as before (`aiProfile.ts`, `legacyProfiles`).
- **Isolation.** Each program is compiled into a directory of its own and runs with only that directory mounted (read-only): no role can list, read or run another's binary. The protocol path already ran its two programs this way.
- **Publication.** Before activation, `profileDifferences` reads the judging settings to be published the way the judge does (a checker's own limits or the problem's, an interactor's time limit at least the problem's) and stops publication if any published program would be judged with other settings than it was checked with (`AI_PROFILE_MISMATCH`).
- **Scoring.** A problem whose judging settings have subtasks of their own has an established scoring policy: each subtask's points (automatic points worked out), scoring type (`Sum`, `GroupMin`, `GroupMul`), dependencies and own limits, and whether samples are judged first. Its SHA-256 (`scoringDigest`) is unchanged by regenerated cases that keep it. The plan is asked for these subtasks when the statement's correspond to them one to one, and keeps them (their points included); both publication paths (traditional and protocol) use `publishedSubtasks`. A plan whose subtasks differ in number, order or points, or settings bound to the replaced cases (a subtask's own limits, test case points or limits), stop the job right after the plan with `AI_SCORING_REVIEW_REQUIRED` and `state.scoringReview` (both policies and why). The owner approves exactly that change by retrying with `retryFrom: "replace-scoring"` (audited with both digests); retried without it, the job plans again after the owner changed the subtasks. A problem without subtasks of its own gets the plan's, each a sum. `data.yaml` records the scoring decision and digest, and the execution profiles with their digest.

## Failure evidence

A failed run of a job's programs is kept as typed observations with their evidence (review Part III, W01), before the run's workspace is cleaned up. The shared contract is `packages/judge-protocol/src/ai-observation.ts`, exported by `@libreoj/judge-protocol`: failure kinds, artifact roles and classifications, limits, `textPreview`, `firstDifference` and `parseAiRunFailure`, which the backend applies to everything a runner sends.

- **Judge.** Each place a failure passes through adds what it knows (`aiFailure.ts`): the sandbox run its program, verdict and measurements, a comparison its input, outputs and the checker's message, the quality checks the program's role, the case and what the output was compared with (`expectedBasis`: an official sample, the candidate oracle or the reference output). `aiEvidence.ts` writes the exact bytes into the run's evidence directory within fixed limits (16 MiB per artifact, 64 MiB and 8 observations per run; a larger artifact keeps its start and says so) and describes them in `failure.json`. A canceled run keeps nothing. A challenge that survives carries its first small failing input as a related `small_counterexample` observation, and whether the extra search stopped at its budget or for lack of a replaceable case. The local runner's directory is `<generated>/<job>/failure`, which the backend reads before it asks for the job's cleanup; a judge machine (protocol 6) uploads it through forms signed for evidence names only, then reports the failure as `AiExecutionProgress.failure`.
- **Backend.** `AiEvidenceService.record` copies each artifact into `temporary/ai-evidence/<observation>/<role>` after checking its size and SHA-256 against the report, and stores the observations in `ai_observation` with IDs derived from the run's attempt, so recording a run twice records it once. Artifacts that can't be stored are recorded as missing, with why; nothing unverified is kept. Evidence is bounded per job (256 MiB, 64 observations) and for the site (2 GiB), and deleted after 14 days (previews and difference excerpts too); the observation stays 90 days. A failure reported while no backend waited is recorded when the job runs again, or by the 10-minute AI run cleanup before it removes the run. Transport and time-limit failures the backend sees itself are recorded without evidence, and a runner that sent none as `unclassified`.
- **Use.** The typed failure decides how the job repairs its programs (see Repairs), and a repair prompt gets the compiler's kept diagnostics without terminal colours (also left out of the job's error message and diagnostics previews; the kept bytes have them). A tutorial's solution that fails its check is recorded with `context: "tutorial-reference"`, not as the failure that ended the job. The job owner reads observations through `ai/failures`, `ai/failureArtifact` (64 KiB parts that end on whole characters) and `ai/downloadFailureArtifact` (a 2-minute link, audited), only while they may still run the job (`AiJobCoordinator.assertEvidenceAccess`).

## Recoverable runs and replay

A job's run of its programs is a logical operation (review Part III, W03), so that a restart, a lost connection or a retry reuses the work that was done instead of starting over with new random cases (`ai-operation.ts`).

- **Operations.** `aiOperationKey` is the SHA-256 of the job, the current AI execution contract and the whole request: every program, case, sample (sample files by the stored files they are) and execution profile. The same request is the same operation; any change is another. Each run on a judge machine (`ai_execution`) records its `operationKey`, its `operation` (`generate`, `validate-reference` or `replay`) and when the job first took its result (`collectedAt`); the columns are added by `deploy/ai-operation-schema.mjs`. When a job asks for an operation, `AiExecutionService` first retires the job's runs of other operations (stops unfinished ones, records failures, removes the rest: another operation never attaches to them), then collects a completed run of the same operation again (only one made under the current contract), waits again for an unfinished one, or takes a failure the job never took as the operation's outcome (once). Otherwise it queues a new attempt. A job that lost its lease leaves its run for the backend that runs the job now.
- **Acknowledgement.** A completed run stays until the job acknowledges it: `AiWorkflowService.execute` calls `acknowledge` only after the checkpoint that marks the test data step completed, so a backend that stops in between (during collection, before or after publication) collects the same result again, and publishes the same bytes. A failed step `release`s its runs (unfinished ones stop; a completed result stays 24 hours, `AI_RESULT_RETENTION`, for a retry of the same operation), and a canceled job `discard`s them. The local runner keeps its completed result (`result.json`, versioned 6) until the backend asks it to clean the job up, with the same effect.
- **Runtime identity.** A completed run reports how it was made (`AiExecutionRecord`, `packages/judge-protocol/src/ai-operation.ts`): the contract, its physical attempt, the runtime (judge program digest, sandbox image, architecture), when, and what it reused; and the exact SHA-256 and size of every case (`corpus`). The workflow refuses a result without them (`INVALID_SANDBOX_RESPONSE`) and publishes only files that are exactly the reported cases. `data.yaml` records `generation.execution` (where the result came from: `new`, `resumed` after the job waited for the same run again, or `collected-again`; the judge task and the backend's runtime record of its judge) and `generation.corpus` (the cases and their digest); the job keeps both in `state.generated`.
- **The judge's checkpoints.** `apps/judge/src/aiCheckpoint.ts` keeps each job's compiled programs by everything their binary depends on (source, compile options, headers, extra sources, grader, judge program and sandbox image), and the inputs each generator made by its build (`GeneratorInputs`: the generator's build key, which covers the runtime), subtask and case index, for runs of keyed operations. An attempt that a restart interrupted runs again with the same builds and replays the same inputs (checks run again on them, never reused); another operation of the same job takes the builds that didn't change and, while its generators are the same builds, their inputs: a run after a repair checks the repaired program on the cases the failed run had. Inputs go when a run that used them completes; builds and inputs when the local backend cleans the job up, or a day after their last use (also on a judge without the local runner, which prunes workspaces a restart left behind too). A new request for a run whose requester is gone (its backend restarted) waits up to 60 seconds for that run to stop.
- **Cancellation** (review Part III, H09). A cancelled job's run stops the program it's running at that moment, not at its next step. The backend closes the local runner's socket when the job's `AbortSignal` fires (`runLocal`), and a run on a judge machine stops waiting at once (`waitFor`'s poll sleep ends on the abort), then cancels the task (`cancelExecution`, the gateway's Redis cancel, `rpc.cancelTask` on the judge). So does the job's own replay on a judge machine (`replay` waits with the job's signal: a replay that tests a repair or confirms a time limit). On the judge, `runGeneration` runs the generation in a cancellation scope (`apps/judge/src/cancelScope.ts`, AsyncLocalStorage) told by the socket's `close` or by `rpc.onCancel`. Every sandbox the run starts with no task ID (compilations, program runs, both programs of a protocol run) stops when the scope is cancelled and rejects with its error. That error is `canceled`, never a verdict: no time limit, crash or killed challenge, and no evidence (`keepFailure`). Work still waiting leaves at once: the generation queue's turn (`runInTurn`), and an execution slot (`ExecutionScheduler.acquire` with the scope; `runTaskQueued` releases a slot granted to a cancelled run and throws). `startSandbox` marks its result promise handled, so a program stopped while its caller still waits for the other one (an interaction) can't end the judge with an unhandled rejection; the caller still gets the rejection.
- **The queue.** A judge client that connects again has lost what it leased through its earlier connection (a judge restarts when it loses its connection), so `JudgeQueueService.releaseEarlierLeases` queues those tasks again at once, for every task type, instead of after their 90-second lease expires (e.g. after the backend restarted).
- **Replay.** `ai/replayFailure` (owner only, as the failures) runs one kept failure again (`AiReplayService`): `replayPlan` (`ai-replay.ts`) decides from the observation what to run (compile a program; validate the kept input with the subtask and case index it was checked with; run a generator with its arguments; run the program on the kept input; compare its output, as the run compared it, with the kept output, another program's output or itself; run the checker on the kept files, which must reject the run's malformed output), with the job's programs as they are now and the problem's profiles as they are now. Only stored, whole artifacts are sent: the local runner gets them as sample files, a judge machine as links signed when it takes the task (`transfers`), each checked against its SHA-256. The runner's operation `replay` runs the check 3 times (a compilation once) and reports each run; the outcome (`reproduced`, `not_reproduced`, `unstable` or `different`), whether the programs and profiles are the ones that failed, where it ran and on what runtime are kept with the observation (its 5 latest replays). One replay runs at a time for each job and each user, none while the job is queued or running (and the job isn't retried during one), none while AI is paused; each is audited (`ai.evidence.replay`). Failures of no single input (a surviving challenge, the budget, the infrastructure, a tutorial's code) and, for interactive and communication problems, anything but compilation and input validation can't be replayed. Judge protocol 8 reports the run record and corpus and runs replays; only judges of protocol 8 are sent AI runs.

## Repairs

A failed run of a test data job is repaired within bounds (review Part III, H02/W04), not by writing every program again. `ai-repair.ts` is the policy, pure and tested alone (`ai-repair.test.cjs`); `AiWorkflowService.runGenerationSandbox` is the loop (`ai-repair-loop.test.cjs`, with a scripted model and runner).

- **Routing.** `routedFailure` takes a run's typed failure (`AiError.failure`), or the backend's own observation (transport errors are `infrastructure_error`, the time limit `budget_exhausted`, an untyped failure `unclassified`); other errors (cancellation, a lost lease, permissions) end the run as before. `routeAiFailure` decides from the kind, role, phase and `expectedBasis` alone: `retry` (the infrastructure, or a compiler that was killed: the same request again, no model request); `repair` one role (a compile error; a validator's rejection of an official sample, or the generator of a rejected generated input, `make` or `quality-small-make` by the phase; a crash or limit of the program itself; an official sample's mismatch with a built-in comparison; a checker failure; an invalid challenge; a surviving challenge whose search stopped at its budget, by repairing `make`); `review` (`ATTRIBUTION` for disagreements of AI-written programs, or a sample's with a custom checker; `PROBLEM_HELPER`; `TUTORIAL_REFERENCE`; `CAPACITY`; `BUDGET`; `UNCLASSIFIED`); or `stop` (canceled). A solution's time or memory limit carries `confirm`: the kept failure is replayed with the current programs first, and one that doesn't reproduce counts as an infrastructure retry. `decideAiRepair` adds the limits (`AI_REPAIR_LIMITS`: 3 automatic, 8 in all, 2 infrastructure retries until the owner retries) and stops (`UNCHANGED`) when the latest revision repaired the same role for the same failure signature (kind, role, candidate, phase, subtask, case index, sample: not the bytes) and the role is still what that revision left.
- **Ownership.** Only programs the job wrote are repaired (`aiWrittenProgram`): `state.problemHelpers` names the helpers the problem's judging settings have (the job writes a helper only where the problem has none), and a tutorial's reference solution is the owner's to replace.
- **A repair** (`repairProgram`) refuses a failure of another version of the program (`STALE`: its kept `sourceHashes`), authorizes, counts the request in `state.repair` and checkpoints before the model request, sends the program's contract (`repairContract`), the failure (`failureContext`: no bytes, excerpts, summary or diagnostics of the problem's own sample files) and the source, with configured keys redacted, and accepts only a different, valid program of the role (`IDENTICAL`, `INVALID`: also kept as rejected revisions). It authorizes again, replaces that one program (`setJobProgram`; a repaired `std` becomes `kind: "model"` and reads stdin) and records the revision (`ai.job.repair` audit). It then replays the kept failure when the failure is the repaired program's own (`testKeptFailure`, kept with the observation and its `repair` round); a reproduced failure stops the job (`UNCHANGED`), anything else runs the whole request again with only that program changed (`syncRequestPrograms`).
- **Review.** A stop records `state.repair.review` (reason, the roles the owner may choose, the observation) and fails the job with the failure it stopped at. `retryOptions` offers `repair` (with `repairRoles`) and `regenerate` (every program written again from the plan); `retryState(job, "repair", role)` queues `state.repair.pending`, which `ownerRepair` makes before the run's profiles are computed. A plain retry of a failed run keeps the programs (the counts too), a plan-level failure deletes the plan and everything written from it, `INVALID_AI_QUALITY_PLAN` the quality plan, its programs and `make`, and a partial-score checker only the checker.
- **Qualification.** `data.yaml` records `generation.revision` (`generationRevision`): the SHA-256 of every program of the request that made the published data, their digest, and the repairs; the job keeps the digest and count in `state.generated.revision`.

## Evidence and cost

A job keeps what its runs did and what its requests were for (review Part III, §8.1/§8.4; `ai-session.ts`, `ai-session.test.cjs`).

- **Requests.** `AiJobCoordinator.withRuntime` wraps a job's usage `record`: each provider request is also counted in `state.spending` by its purpose (`purposeOfStep` of the job's step when it was made: plan, programs, repairs, tutorial, translate, …): requests, failed ones, searches, reported tokens, and requests without reported usage. `ai_usage` stays the record: `AiUsageService.jobTotals` sums each listed job's rows (one grouped query per `ai/jobs`), and the difference from the counted ones is shown as "other" (state isn't saved when a job fails, so its last requests may be uncounted).
- **Request identity (review Part IV, W01).** Each provider request carries its `purpose`, fixed when it's sent (`currentAiPurpose`: `withAiPurpose`, else the runtime's `purpose()`, which for a job is `purposeOfStep` of its step at that moment), and a `generationId` that `generateText` gives one generation and every poll recovering its response. Both are recorded in `ai_usage` (`deploy/ai-usage-identity-schema.mjs`). `tallyUsage` and `AiUsageService.jobTotals` count `generations` (`operation = 'generate'`) apart from `requests` (every model request, polls included), and `unreported` per generation: resolved when any of its requests reported usage (rows from before have no `generationId` and count one by one). `jobTotals` also returns `purposes` (generations and requests by recorded purpose), which the evidence line prefers to `state.spending`, so the last request before a failure is attributed too. Response-hash deduplication of recovered responses is unchanged.
- **Plan issues (W01).** `validateAiQualityPlan` (`ai-testdata-quality.ts`) applies the plan's unchanged rules and returns every failure as `{ path, rule, expected, actual, repairClass }` (at most 40, sizes and short values only). A rejected answer is kept in `state.planProposal` (issues, a digest, the answer itself up to 64 KiB) and counted in `state.planRejections` before the job fails with `AiPlanError` (`INVALID_AI_QUALITY_PLAN: N invalid fields: …`); an accepted plan removes the proposal. The job view returns `planIssues` and `planRejections`.
- **Runs.** `runGenerationSandbox` and `testKeptFailure` append each run to `state.runs` (`recordRun`, the 20 latest): when, generate or replay, seconds from request to result, "passed" or the failure kind (a replay: its outcome), origin and reuse when the run reported them, and the repair whose program it ran first (or that the replay tested).
- **Changes.** `repairProgram` keeps each accepted repair's `unifiedDiff` (3 lines of context; the common start and end found first, the rest compared by longest common subsequence up to 4,000,000 line pairs, else shown as replaced; at most 64 KiB, whole lines). `ai/jobs` carries only each change's size; `ai/repairChange` (`jobId`, `round`; owner, as the failures) returns its text.
- **Inbox.** The job list counts failed jobs with a repair or scoring review, and can show only those.

## Tutorials and the reference solution

A job's tutorial is published before its test data, and `tryTutorialReference` may reject its code on the official samples and fall back to a model-written reference solution, which a repair may replace again (review Part III, H08). What a published tutorial's code passed is kept with the job (`ai-tutorial-binding.ts`, `ai-tutorial-binding.test.cjs`; job state, no schema change):

- **Binding.** Publishing each language version records `state.tutorialBindings`: the discussion, its locale, and the SHA-256 of its first C++ implementation, as `tutorialCppCandidates` extracts it from the published content (null when it has none). A job from before this has its bindings from its kept `tutorialContents` (`tutorialBindingsOf`).
- **Checks.** `tryTutorialReference` records each candidate it ran in `state.tutorialChecks` by SHA-256: `passed` with the samples, or `rejected` with the failure's kind, subject, message and observation ID (the observation is kept with `context: "tutorial-reference"`).
- **Status** (`tutorialCodeStatus`, computed from the current state, so a repair or regeneration keeps it current): `no-code`, `unchecked`, `passed-samples` (no test data published), `rejected`, `qualified` (the published test data's std.cpp, `state.stdCode` with `state.generated`, is exactly this code) or `superseded` (it's another program: a fallback, a repair or a regeneration). `serialize` gives the owner `result.tutorials` and `result.tutorialCorrection`. `ai/tutorialStatus` gives anyone who may view the discussion its status alone (null for a discussion no AI job published); it reads only the problem's jobs' bindings and tutorial IDs, then the one job. The texts say what the code passed and never that the proof is verified.
- **Correction.** `ai/correctTutorial` (owner, completed job) reopens only the tutorial step (`tutorialCorrectionState`: `tutorial` out of `completed`, `state.tutorialCorrection` set; `requeue` accepts a completed job here) when a tutorial is `rejected` or `superseded`, the job published test data, and, for a problem judged with named files, the reference solution reads and writes them (`tutorialCorrectionRefusal`: `NOTHING_TO_CORRECT`, `NO_REFERENCE`, `FILE_IO`). `correctTutorialCode` sends the tutorials and the reference solution in one request; the model returns each tutorial with the placeholder `<!-- REFERENCE SOLUTION -->` where the code goes, and `correctedTutorial` puts exactly `stdCode` there and accepts only a result whose sole C++ implementation is that code (`INVALID_AI_TUTORIAL: CODE_NOT_REFERENCE`), that obeys the tutorial facts. Each discussion is updated in place (`updateDiscussionTitleAndContent`: same ID, title, type and visibility) after its modify permission is checked again, its binding records `corrected` (when, and the former SHA-256), and each is audited (`tutorial.correct`). No other step runs.

`aiProfile.test.cjs` also checks the judging contract against the judge's own reading of judging settings (checker limits, interactor limits, compile parameters).

Run that command from the repository root. CI runs both the backend mock suite and this judge suite, as documented in the bilingual development guides. Real sandbox acceptance requires a dedicated execution environment and verifies compilation, actual resource verdicts and checker behavior separately.

The mock tests use synthetic keys. MariaDB tests are opt-in through their documented test configuration environment variables and create temporary tables; select a disposable test database. The attachment cases of `ai-actions.mariadb.test.cjs` extract real ZIP archives in the system temporary directory (or the directory of `HYHOJ_AI_TEST_RESULTS`), and extraction keeps 2 GiB free, so set `TMPDIR` to a larger filesystem when `/tmp` is a small tmpfs.

The `.mjs` integration suites additionally require an explicitly configured disposable backend, test fixture users and sandbox runner. `test/integration-client.mjs` requires all of:

- `HYHOJ_TEST_CONFIG`: a private backend YAML file whose database name starts with `hyhoj_test_` and whose database host is a numeric loopback address.
- `HYHOJ_TEST_STATE`: a private JSON file with `users` and `tokens` maps for newly created test accounts. Do not reuse production sessions or include this file in the repository.
- `HYHOJ_TEST_BASE`: the loopback origin of the dedicated test backend or frontend proxy, without URL credentials, query or path.

Use a dedicated local Redis instance configured with an explicit nonzero logical database. The client rejects the former installation's service ports. It validates the configuration before connecting and refuses HTTP redirects. The default AI fixture account is `ai_fixture`; `HYHOJ_AI_FIXTURE_USER` can select another dedicated test account, but `admin` is rejected. The synthetic provider on loopback port `2230` works without an address allowlist.

Browser integration requires Playwright available as a local backend development dependency. Screenshots are saved only when `HYHOJ_TEST_EVIDENCE_DIR` is set to a directory outside the repository. After integration tests, remove the disposable test database, sessions and temporary files.

## NOI contest Self Eval integration

Successful traditional-data publication binds immutable, hash-checked copies of the exact generator, standard solution and validator used by that job. The enabled NOI / OI contest problem’s Self Eval dialog can explicitly start the existing `testdata` workflow through its AI button, regenerate formal data, reload matching make/std sources and then prepare the fixed hidden prediction set before the contest begins. The prediction judge reuses the problem’s formal checker/SPJ; handwritten configuration needs only make/std, with the bound formal validator reused when available. The generator and validator run with the limits the job checked them with (`selfEval.limits`). This binding does not expose ordinary problem-bank Self Eval or alter official scores. Runtime/API scope and quotas are enforced independently by SelfEvalService. See the bilingual [Self Eval guide](../../../../wiki/Self-Evaluation.md).
